# 技术路线：为什么是现在这条路

记录**路线级判断**——哪条路能走、哪条走不通、为什么。
避免每隔几个月重新调研一遍同样的问题。

---

## 结论（2026-08-23）

**执行层用 adb + 控件树优先/截图兜底，是当前唯一可行的路线。换硬件不改变任何事。**

瓶颈不在设备，在两处，且都无法用换机解决：

| 瓶颈 | 原因 | 换手机能解吗 |
|---|---|---|
| Flutter/H5 自绘页面读不到控件树 | 渲染层不产生 AccessibilityNode | ❌ 任何安卓机都一样 |
| 即时私信对话慢（1-2 分钟/条） | 模型往返延迟 | ❌ 与设备无关 |

**能力边界**：适合批量发布、一处改动同步多平台、定时执行、无人值守；不适合抢时效的实时对话。

## 值得引入的路线：端到端 GUI Agent 模型（截图入 → 动作出）

> 2026-08-23 补：本文件初版遗漏了这条路，只写了硬件和 AppFunctions。**这条路已有成熟开源实现，不是空白。**

### 有哪些

| 模型 / 框架 | 来源 | 状态 |
|---|---|---|
| **Open-AutoGLM** | 智谱 AI | 开源，**专门适配 50+ 款中文主流 App**，支持 WiFi 远程 ADB。**最对口本项目** |
| AutoGLM-Phone 9B | 智谱 | 端侧模型，可 vLLM 本地部署 |
| UI-TARS | 字节 Seed + 清华 | 豆包 AI 手机的核心技术，已开源 |
| UI-Genie | vivo AI Lab + 港中文 | 自进化，无需人工标注 |

配套：AutoGLM-GUI（Web 界面 + scrcpy 实时镜像 + 定时任务 + 多设备管理）

另（2026-09-06 搜索发现，未实测）：**agent-device**（Callstack 开源，MIT，~4k star）——专门给 AI Agent 用的设备自动化 CLI，iOS/Android/TV/桌面全覆盖，JPMorgan/Shopify 团队在用，定位取代 Appium。与本项目工具层同赛道，值得实测对比。

### 实际水平（2026 年数据，别看宣传看这个）

| 测试环境 | 成功率 |
|---|---|
| AndroidWorld（标准 benchmark，环境干净） | 顶级 agent 80~91% |
| **MobiFlow（2026-02，真实 App 环境）** | **UI-TARS 60.4%，GUI-OWL 55.7%** |

单步执行 **1.75 秒**——与本项目截图视觉方案同量级，无数量级优势。

**实验室 90% / 真实 60% 的落差是常态。60% 意味着 10 次任务 4 次需人工接管。**

### 🔬 实测结论：换 GUI 专用模型没有收益（2026-08-23，已验证，别再试第二遍）

百炼的 `gui-plus` vs 现用的 `qwen3-vl-plus`，同一张小红书首页截图、12 个目标（含底部导航、顶部密集 tab、内容区作者名），控件树 bounds 做真值：

| | gui-plus | **qwen3-vl-plus（现用）** |
|---|---|---|
| 命中 | 12/12 | 12/12 |
| 平均偏差 | 69px | **65px** |
| 平均耗时 | 3.9s | **2.8s** |
| 平均 token | 9024 | **2599** |

**精度打平，现用方案快 28%、便宜 3.5 倍。→ 维持 `qwen3-vl-plus`，不换。**

两个注意点：
- 后 4 个内容区目标两模型偏差几乎相同（153/152、269/272、160/151、155/154），说明**偏差来自控件树 bounds 中心 ≠ 文字视觉中心**（如"热点"的 bounds 宽 578px），不是模型误差，两者均命中 bounds。
- 测试脚本：`scratchpad/bench_gui.py`（对照测试）、`coord_probe.py`（坐标系探针）。要复测换个 App 直接改目标词即可。

### 与本项目的关系：互补，不是替代

| | 通用 GUI Agent | 本项目手册 + 固化脚本 |
|---|---|---|
| 没碰过的 App | ✅ 直接可摸 | ❌ 需先探索 |
| 已摸熟的 App | 60%，每次重新"看" | **接近 100%，直接调坐标** |
| 速度 | 1.75 秒/步 | 小红书 < 1 秒/步 |

**正确用法：用 GUI Agent 探索新 App → 跑通的路径写进 `core/apps/<App>.md` → 之后走固化脚本。**
即"探索 → 写文档 → 照文档执行"（腾讯 AppAgent 论文的方法论），与本项目 CLAUDE.md 的设计一致。

**结论：用积累把 60% 变成 100%，这是本项目存在的意义。**

### 为什么端到端模型也到不了 FSD 的水平

| 维度 | 特斯拉 FSD | 手机 GUI Agent |
|---|---|---|
| 推理位置 | 车载芯片，10ms/帧 | 云端，1750ms/步，**差 100 倍** |
| 容错 | 连续控制，下一帧可修正 | **操作不可逆**（消息已发、款已付、帖已发） |
| 数据 | 百万辆车回传真实路况 | 无同等规模标注数据（UI-Genie 论文的核心痛点） |

## 已评估并否决的路线

### Pixel 11（2026-08-12 发布）—— 否决

Gemini Intelligence 的"跨 App 代办"覆盖 40 余个 App，**全是 Google 自家 + 美国合作方**（订杂货 / 叫车 / 买咖啡 / 代打电话订餐厅），仅限美国。国内 App 不在其中且不会进入。

对本项目**净负收益**：
- 国内 App 需侧载，缺 GMS 推送，冷门机型风控更敏感
- 执行层仍是 adb，代码一行不用改，速度一点不提

唯一有价值的点：Gemini 可代拨电话 + 实时转写 + 随时接管（美国 / 英文限定）。

### 国内 AI 手机（荣耀 YOYO / vivo PhoneGPT / 小米超级小爱 / 豆包手机 / 阶跃 STEPX Neo）—— 同源，无质变

**它们的技术方案与本项目相同**：无障碍服务读控件树 + 模拟点击。天花板一致——慢、脆、App 改版即失效。
（21 世纪经济报道 2025 全年追踪，定性为"对无障碍权限的灰色调用"）

比本项目多的只有两样，且都不是技术优势：
1. 跑在系统内，省掉 adb 往返的一跳
2. **与大厂签 A2A 协议**——微信已与华为/荣耀/小米/OPPO/vivo 达成，支持语音发消息、发起音视频

→ **能力来自谈判，不来自技术。** 个人无法复制第 2 条。

### 接口/MCP 路线（xiaohongshu-mcp 类）—— 用户已明确否决

用户要求"操控平板"，不走接口。且接口路线有账号风险。
注：`~/claude/mcp/xiaohongshu-mcp` 是**另一个项目**的能力，与本项目路线无关，不要混用。

## 真正的天花板：平台反制（对所有路线都适用）

技术不是墙，**App 厂商的对抗才是**。

实证（2025 年底，吾爱破解论坛用户实测记录）：豆包 AI 手机工程机初期可代打游戏、跨 App 办事，随后遭厂商封杀——**微信封号、金融类 App 限制、购物软件限制**。

这与 AppFunctions 无人接入是同一个根因：**App 的商业模式依赖用户亲自打开它、刷它的信息流。让 AI 代操作 = 让出流量入口。**

**推论**：任何方案（自研脚本 / 开源 GUI Agent / 厂商智能体 / AppFunctions）都受此约束。
→ 因此本项目坚持：低频、拟人节奏、加随机延迟、不做高频轮询、绝不碰支付与登录。

## 唯一的结构性解法：AppFunctions（不在我们控制范围内）

Android 16 框架，Google 2026-02 正式推出。App 主动声明可被 AI 调用的能力，本质是系统级 MCP——不读屏、不猜坐标，直接调用 `publishNote(title, body, images)` 这类函数。
文档：https://developer.android.com/ai/appfunctions

**技术上完全成立，卡在利益上**：需 App 开发者主动接入。小红书、闲鱼的商业模式依赖把用户留在自身信息流内，暴露发布接口 = 让出流量入口，因此不会接。

**判断依据**：本项目"对 AI 不友好"的根因是国内 App 不愿让 AI 代用户操作它，不是硬件、系统或模型的问题。
**复查触发条件**：若某天小红书 / 闲鱼 / 微信公布 AppFunctions 支持，立刻重估整条路线。在此之前不必再调研手机硬件。
